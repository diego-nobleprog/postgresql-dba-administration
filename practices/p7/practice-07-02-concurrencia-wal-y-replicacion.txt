PostgreSQL DBA Administration

REGLA PARA COPIAR COMANDOS

Ejecutar SQL dentro de psql y comandos Docker en PowerShell.
No copiar los prompts ni las explicaciones.

Los metacomandos de psql se ejecutan INDIVIDUALMENTE.
Esto incluye \q, \set y la sentencia que termina con \gset.
Pegar esa instruccion sola, pulsar Enter y esperar el prompt
antes de pegar la siguiente consulta.

Los bloques que contienen solamente SQL pueden pegarse completos.
Un prompt con * indica una transaccion abierta.
Un prompt con - indica una sentencia incompleta.
Si hay texto accidental pendiente, pulsar Ctrl+C y esperar
el prompt antes de pegar nuevamente el SQL.


OBJETIVO

Relacionar una transaccion abierta con visibilidad de datos,
bloqueos, wait events y aplicacion de WAL en la replica.

SITUACION

Un empleado registra un pago y no confirma todavia.
Otro intenta modificar el mismo pedido.
Mientras tanto, un supervisor consulta los totales.

La pregunta central es:
Si una operacion espera, el problema siempre es una consulta lenta?

CONCEPTOS NECESARIOS

Transaccion: grupo de operaciones que termina con COMMIT
o ROLLBACK.

MVCC: permite lecturas consistentes mediante versiones.
Una lectura ordinaria no ve cambios no confirmados de otra sesion.

Lock: coordina operaciones concurrentes.
Wait event: indica en que esta esperando un proceso.

WAL: registro utilizado para recuperacion y replicacion.
Puede generarse y transmitirse antes del COMMIT.
Eso no hace visibles los cambios no confirmados en el standby.

Streaming asincrono: el principal no espera el replay del
standby para confirmar cada transaccion.

Replication slot: conserva WAL necesario para el consumidor,
dentro de los limites configurados. No significa retraso cero
ni ausencia garantizada de perdida de datos.

3. CAMBIO SIN COMMIT
============================================================

FROM negocio.pedidos

INTERPRETACION

A ve su propio cambio: 900 + 200.
La transaccion sigue abierta y conserva el bloqueo.

SESION C - PSQL SOBRE SERVIDOR A

SELECT sum(total) AS venta_pagada

WHERE estado='PAGADO' AND fecha=DATE '2026-01-15';

SERVIDOR B - PSQL

RESULTADO ESPERADO: 900.

============================================================
4. GENERAR LA ESPERA
============================================================

SESION B - PSQL SOBRE SERVIDOR A

SET statement_timeout='5min';

UPDATE negocio.pedidos
SET estado='PAGADO'
WHERE id=101;

RESULTADO ESPERADO

El UPDATE queda esperando; no vuelve inmediatamente el prompt.

No ejecutar otros comandos en esta sesion mientras espera.
Continuar en la SESION C.

SESION C - PSQL SOBRE SERVIDOR A

SELECT pid,application_name,state,wait_event_type,wait_event,
       pg_blocking_pids(pid) AS bloqueadores
FROM pg_stat_activity
WHERE application_name IN ('p7_sesion_A','p7_sesion_B')
ORDER BY application_name;

RESULTADO ESPERADO

A: idle in transaction.
B: active, wait_event_type Lock.
B identifica el PID de A entre sus bloqueadores.
Es habitual observar wait_event transactionid.

Consultar los locks:

SELECT l.pid,l.locktype,l.mode,l.granted
FROM pg_locks l
JOIN pg_stat_activity a USING(pid)
WHERE a.application_name IN ('p7_sesion_A','p7_sesion_B')
ORDER BY l.pid,l.granted;

INTERPRETACION

granted=false significa que ese bloqueo esta solicitado
y aun no fue concedido.

El indice de 07.01 ayuda a localizar datos.
No permite saltarse un bloqueo incompatible.

Esto es una espera por lock, NO un deadlock:
no existe un ciclo de dependencias.

RETO PARA LOS PARTICIPANTES

Identificar quien bloquea y justificarlo con los PID.
No concluir que A esta esperando a B porque B siga activo.

Si se agotan los cinco minutos:
cancelar y revisar el estado antes de continuar.
Si A sigue abierta, ejecutar ROLLBACK en A, salir de las
sesiones y revisar la incidencia; no repetir cambios a ciegas.

============================================================
7. AFTER - WAL Y ESTADO DE LA REPLICACION
============================================================

SESION C - PSQL SOBRE SERVIDOR A

SELECT pg_wal_lsn_diff(
    pg_current_wal_lsn(), :'wal_inicio'::pg_lsn
) AS avance_wal_bytes;

SELECT application_name,state,sync_state,sent_lsn,replay_lsn
FROM pg_stat_replication;

SELECT slot_name,slot_type,active,restart_lsn
FROM pg_replication_slots;

SELECT * FROM pg_stat_checkpointer;

RESULTADO ESPERADO

Avance WAL positivo.
Conexion de B en streaming, sync_state async.
Slot integrado_b fisico y activo.

El avance WAL incluye la actividad registrada durante
el intervalo; no es el tamano exacto del pedido 105.

pg_stat_checkpointer ofrece contadores acumulados.
Esta consulta no demuestra que una escritura concreta
haya provocado un checkpoint.

SERVIDOR B - PSQL

SELECT status,sender_host,sender_port
FROM pg_stat_wal_receiver;

RESULTADO ESPERADO

streaming, 127.0.0.1, 5547.

COMPARACION CON ORACLE

En ambos motores una transaccion puede impedir el avance
de otra operacion incompatible.

Las vistas, tipos de espera y mecanismos internos difieren.
pg_stat_activity y pg_locks se usan aqui para observar PostgreSQL.
No trasladar literalmente sus nombres a Oracle.

El transporte y aplicacion de redo en Data Guard aportan
una referencia conceptual para distinguir envio y aplicacion
de WAL en PostgreSQL.

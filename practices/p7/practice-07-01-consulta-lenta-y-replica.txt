======================================================================
1. OBJETIVO DEL LABORATORIO
======================================================================

Una empresa administra los pedidos de sus clientes mediante PostgreSQL.

Diariamente necesita consultar los pedidos pagados, identificar
al cliente correspondiente y conocer el importe de cada operacion.

Sin embargo, conforme aumenta la cantidad de pedidos almacenados,
el reporte comienza a realizar mas trabajo del necesario.

El objetivo de este ejercicio es investigar ese comportamiento,
identificar una oportunidad de optimizacion y comprobar que
la mejora tambien se encuentra disponible en una replica fisica.

Durante el laboratorio los participantes aprenderan a:

1. Consultar los datos originales de un sistema de pedidos.
2. Identificar las operaciones realizadas por una consulta SQL.
3. Interpretar EXPLAIN y EXPLAIN ANALYZE.
4. Analizar los accesos a buffers de PostgreSQL.
5. Identificar un recorrido secuencial de una tabla.
6. Crear un indice compuesto B-tree.
7. Comparar el rendimiento BEFORE y AFTER.
8. Interpretar estadisticas de pg_stat_statements.
9. Comprobar que el indice se replica a PostgreSQL B.
10. Verificar que el standby acepta lecturas, pero no escrituras.

REGLA PRINCIPAL

La optimizacion debe mejorar la forma de acceder a los datos,
sin modificar los resultados del negocio.

Los pedidos pagados deben continuar siendo los mismos.
El importe total de ventas debe permanecer en 900.

6. BEFORE - DIAGNOSTICAR LA CONSULTA LENTA
======================================================================

La empresa necesita mostrar los pedidos pagados
individualmente, incluyendo el nombre del cliente.

Actualmente PostgreSQL tiene 50004 pedidos y
solamente tres cumplen el filtro solicitado.

Queremos investigar cuanto trabajo realiza
el servidor para obtener esas tres filas.

----------------------------------------------------------------------
PASO 6.1 - CONSULTAR EL PLAN ESTIMADO
----------------------------------------------------------------------

SERVIDOR A - PSQL

EXPLAIN
SELECT c.nombre, p.id, p.fecha, p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id = p.cliente_id
WHERE p.estado = 'PAGADO'
  AND p.fecha = DATE '2026-01-15'
ORDER BY p.fecha, p.id;

EXPLICACION

EXPLAIN solicita al optimizador de PostgreSQL
que muestre el plan de ejecucion estimado.

En esta modalidad no ejecuta la consulta SELECT.

El plan describe como PostgreSQL pretende obtener
los registros solicitados.

Entre los operadores que podemos encontrar estan:

Seq Scan:
Recorrido secuencial de las filas de una tabla.

Index Scan:
Acceso a registros utilizando un indice.

Hash Join:
Relacion entre tablas utilizando una estructura hash.

Nested Loop:
Relacion entre tablas mediante busquedas repetidas.

Sort:
Ordenamiento de registros.

Los operadores concretos pueden variar segun
las decisiones del optimizador.

RESULTADO ESPERADO

Para negocio.pedidos esperamos observar un Seq Scan
o recorrido secuencial, ya que todavia no existe
el indice compuesto sobre estado y fecha.

La tabla clientes solamente contiene tres filas.

Un Seq Scan sobre clientes no representa necesariamente
un problema de rendimiento.

----------------------------------------------------------------------
PASO 6.2 - EJECUTAR Y MEDIR LA CONSULTA
----------------------------------------------------------------------

SERVIDOR A - PSQL

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.nombre, p.id, p.fecha, p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id = p.cliente_id
WHERE p.estado = 'PAGADO'
  AND p.fecha = DATE '2026-01-15'
ORDER BY p.fecha, p.id;

EXPLICACION

EXPLAIN:
Muestra el plan de ejecucion.

ANALYZE:
Ejecuta realmente la consulta y recopila
mediciones de su funcionamiento.

BUFFERS:
Muestra informacion sobre los buffers consultados
durante la ejecucion.

Como estamos utilizando SELECT, esta medicion
no modifica los pedidos.

ELEMENTOS QUE DEBEMOS IDENTIFICAR

1. Seq Scan on pedidos

Indica que PostgreSQL examino secuencialmente
la tabla de pedidos.

2. Filter

Muestra las condiciones utilizadas para
seleccionar solamente los pedidos pagados
de la fecha indicada.

3. Rows Removed by Filter

Indica cuantas filas fueron descartadas
por no cumplir las condiciones.

En este escenario esperamos aproximadamente 50001
filas descartadas en el recorrido de pedidos.

4. Actual Rows

Indica cuantas filas produjo realmente un operador,
por cada ejecucion de ese operador.

La consulta completa debe devolver tres filas.

5. Actual Loops

Indica cuantas veces se ejecuto un operador.

6. Execution Time

Indica el tiempo total medido para la ejecucion.

7. Buffers: shared hit

Indica accesos a bloques que PostgreSQL encontro
en sus buffers compartidos.

8. Buffers: shared read

Indica bloques que PostgreSQL tuvo que incorporar
a sus buffers compartidos.

Una lectura reportada aqui no demuestra necesariamente
una lectura fisica desde el disco, porque el sistema
operativo tambien puede utilizar cache.

9. Sort

Si aparece, indica que PostgreSQL realizo
una operacion de ordenamiento.

10. Join

Indica como se relacionaron las tablas
pedidos y clientes.

IMPORTANTE SOBRE LOS COSTOS

El valor cost mostrado por EXPLAIN representa
una estimacion interna del optimizador.

No esta expresado directamente en milisegundos.

Tampoco debemos sumar indiscriminadamente
los buffers mostrados en nodos padres e hijos,
porque sus contabilizaciones pueden incluir
el trabajo realizado por operadores descendientes.

7. CAMBIO - CREAR UN INDICE COMPUESTO B-TREE
======================================================================

Ahora realizaremos un cambio controlado sobre
la estructura de acceso a los datos.

No modificaremos los registros de negocio.

----------------------------------------------------------------------
PASO 7.1 - CREAR EL INDICE
----------------------------------------------------------------------

SERVIDOR A - PSQL

CREATE INDEX pedidos_estado_fecha_idx
ON negocio.pedidos (estado, fecha);

EXPLICACION

CREATE INDEX:
Solicita la creacion de un indice.

pedidos_estado_fecha_idx:
Nombre asignado al nuevo indice.

ON negocio.pedidos:
Indica la tabla sobre la que sera creado.

(estado, fecha):
Indica las dos columnas incluidas en el indice.

Se trata de un indice compuesto porque utiliza
mas de una columna.

PostgreSQL utiliza B-tree de manera predeterminada
cuando CREATE INDEX no especifica otro metodo.

POR QUE ESTAS COLUMNAS

Nuestra consulta contiene:

WHERE estado = 'PAGADO'
  AND fecha = DATE '2026-01-15'

Por tanto, el indice ofrece una forma de localizar
los registros que cumplen ambas condiciones,
sin tener que examinar necesariamente toda la tabla.

El optimizador decide si conviene utilizarlo.

RESULTADO ESPERADO

CREATE INDEX

IMPORTANTE

Crear un indice tiene un costo de almacenamiento.

Tambien introduce trabajo adicional cuando se
insertan, actualizan o eliminan registros afectados.

Por eso no debemos crear indices indiscriminadamente.

----------------------------------------------------------------------
PASO 7.2 - COMPROBAR LA DEFINICION DEL INDICE
----------------------------------------------------------------------

SERVIDOR A - PSQL

SELECT indexname,
       indexdef
FROM pg_indexes
WHERE schemaname = 'negocio'
  AND tablename = 'pedidos'
  AND indexname = 'pedidos_estado_fecha_idx';

EXPLICACION

pg_indexes:
Vista que permite consultar los indices existentes.

schemaname:
Esquema al que pertenece la tabla.

tablename:
Nombre de la tabla.

indexname:
Nombre del indice que buscamos.

indexdef:
Definicion SQL del indice.

RESULTADO ESPERADO

Debe aparecer el indice pedidos_estado_fecha_idx.

Su definicion debe indicar que utiliza B-tree
sobre las columnas estado y fecha.

----------------------------------------------------------------------
PASO 7.3 - CONFIRMAR QUE LOS DATOS NO CAMBIARON
----------------------------------------------------------------------

SERVIDOR A - PSQL

SELECT count(*) AS pedidos_pagados,
       sum(total) AS venta_pagada
FROM negocio.pedidos
WHERE estado = 'PAGADO'
  AND fecha = DATE '2026-01-15';

RESULTADO ESPERADO

pedidos_pagados    venta_pagada
--------------------------------

INTERPRETACION

El indice no modifico los pedidos.

Antes de crear el indice teniamos:

3 pedidos pagados.
900 de importe total.

Despues de crear el indice seguimos teniendo:

3 pedidos pagados.
900 de importe total.

Por tanto, el cambio afecta las posibilidades
de acceso a los datos, no los datos del negocio.

8. AFTER - REPETIR EL DIAGNOSTICO
======================================================================

Ahora ejecutaremos exactamente la misma consulta
utilizada durante el diagnostico BEFORE.

Esto permite comparar el comportamiento antes
y despues de crear el indice.

----------------------------------------------------------------------
PASO 8.1 - MEDIR NUEVAMENTE
----------------------------------------------------------------------

SERVIDOR A - PSQL

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.nombre, p.id, p.fecha, p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id = p.cliente_id
WHERE p.estado = 'PAGADO'
  AND p.fecha = DATE '2026-01-15'
ORDER BY p.fecha, p.id;

QUE BUSCAR

En este conjunto de datos esperamos observar
que PostgreSQL aproveche el nuevo indice.

Entre los operadores posibles estan:

Index Scan.

Bitmap Index Scan combinado con Bitmap Heap Scan.

El plan exacto depende del optimizador y
de las condiciones de ejecucion.

La consulta debe continuar devolviendo tres filas.

QUE PUEDE CAMBIAR

El tiempo de ejecucion puede disminuir.

La cantidad de bloques examinados puede disminuir.

La estrategia de JOIN puede cambiar.

La presencia de un operador Sort puede mantenerse.

POR QUE PUEDE CONTINUAR APARECIENDO SORT

Nuestro indice contiene:

estado, fecha.

Pero la consulta ordena utilizando:

fecha, id.

El indice elegido no garantiza por si mismo
el ordenamiento completo solicitado.

Por eso es posible que PostgreSQL siga utilizando
una operacion Sort.

Esto no invalida la optimizacion del filtrado.

----------------------------------------------------------------------
PASO 8.3 - COMPARACION BEFORE Y AFTER
----------------------------------------------------------------------

INTERPRETACION

La diferencia importante es que ahora PostgreSQL
dispone de un indice que permite localizar
directamente los registros del filtro.

Por ejemplo, si un plan pasa de examinar decenas
de miles de filas a recuperar solamente unas pocas
mediante un indice, existe una mejora en el
trabajo de acceso a los registros.

Sin embargo, los tiempos pueden cambiar debido
a cache, CPU, I/O y condiciones del equipo.

Los valores BEFORE y AFTER deben obtenerse
de la ejecucion real de los participantes.

No se exige una cantidad fija de milisegundos
ni se asume que todos los equipos mediran lo mismo.

----------------------------------------------------------------------
PASO 9.2 - CONSULTAR LAS ESTADISTICAS ACUMULADAS
----------------------------------------------------------------------

SERVIDOR A - PSQL

SELECT calls,
       rows,
       round(total_exec_time::numeric, 3) AS total_ms,
       shared_blks_hit,
       shared_blks_read,
       left(query, 100) AS consulta
FROM pg_stat_statements
WHERE dbid = (
    SELECT oid
    FROM pg_database
    WHERE datname = current_database()
)
AND query LIKE 'SELECT c.nombre,p.id%'
ORDER BY calls DESC;

EXPLICACION

pg_stat_statements:
Vista que contiene estadisticas acumuladas
de sentencias SQL registradas por PostgreSQL.

calls:
Cantidad de ejecuciones registradas.

rows:
Cantidad acumulada de filas devueltas o afectadas
por las ejecuciones registradas.

total_exec_time:
Tiempo acumulado de ejecucion en milisegundos.

::numeric:
Convierte el valor a tipo numeric.

round(..., 3):
Presenta el tiempo con tres decimales.

shared_blks_hit:
Cantidad acumulada de accesos a bloques
encontrados en buffers compartidos.

shared_blks_read:
Cantidad acumulada de bloques leidos
hacia los buffers compartidos.

left(query, 100):
Muestra solamente los primeros 100 caracteres
del texto de la consulta para facilitar su lectura.

dbid:
Identifica la base de datos asociada a las estadisticas.

current_database():
Devuelve el nombre de la base de datos actual.

LIKE:
Permite localizar las consultas que comienzan
con el texto especificado.

ORDER BY calls DESC:
Presenta primero las consultas con mas llamadas.

RESULTADO ESPERADO

La consulta ejecutada mediante el archivo SQL
debe aparecer con al menos tres llamadas registradas.

Tres ejecuciones que devuelven tres filas cada una
aportan nueve filas a las estadisticas acumuladas.

Puede haber mas llamadas porque la consulta tambien
se ejecuto durante otros pasos del laboratorio.

Los tiempos y buffers no tienen valores fijos.

INTERPRETACION

EXPLAIN ANALYZE permite investigar una ejecucion.

pg_stat_statements permite observar el comportamiento
acumulado de consultas ejecutadas repetidamente.

Esto resulta util para identificar sentencias
que consumen recursos de forma frecuente.

Las estadisticas pertenecen a la instancia consultada.

Los literales SQL pueden aparecer normalizados
como parametros dentro del texto registrado.

======================================================================
10. COMPROBAR LA REPLICACION FISICA
======================================================================

Ya optimizamos la consulta en PostgreSQL A.

Ahora debemos comprobar que el indice tambien
se encuentre disponible en PostgreSQL B.

Este paso relaciona directamente:

MODULO 6 - PERFORMANCE TUNING.

MODULO 7 - REPLICACION.

----------------------------------------------------------------------
PASO 10.1 - VERIFICAR EL ESTADO DE STREAMING REPLICATION
----------------------------------------------------------------------

SERVIDOR A - PSQL

SELECT application_name,
       state,
       sync_state
FROM pg_stat_replication;

EXPLICACION

pg_stat_replication:
Vista del servidor principal que muestra informacion
sobre las conexiones de replicacion.

application_name:
Identifica la conexion del standby.

state:
Muestra el estado del proceso WAL Sender.

sync_state:
Indica la modalidad de sincronizacion
asociada a la conexion.

RESULTADO ESPERADO

application_name    state        sync_state
--------------------------------------------
integrado_B         streaming    async

INTERPRETACION

PostgreSQL B mantiene una conexion de replicacion
con PostgreSQL A.

streaming indica que el WAL Sender esta transmitiendo
informacion mediante streaming replication.

async indica que la replica utiliza
replicacion asincrona.

Esto significa que las transacciones del principal
no necesitan esperar a que B reproduzca sus cambios
para que el COMMIT termine.

----------------------------------------------------------------------
PASO 10.2 - ESPERAR LA SINCRONIZACION
----------------------------------------------------------------------

Abrir una segunda terminal PowerShell.

Desde esa terminal ejecutar:

docker exec -u postgres p7-integrado-lab bash /tmp/p7-integrado-scripts/aux-verify-standby-synchronization.sh

EXPLICACION

docker exec:
Ejecuta un programa dentro del contenedor.

-u postgres:
Utiliza el usuario Linux postgres.

bash:
Ejecuta el script indicado.

aux-verify-standby-synchronization.sh:
Comprueba la identidad y el estado de los servidores
y espera hasta que B reproduzca una posicion WAL de A.

El script utiliza:

pg_current_wal_lsn() en A.

pg_last_wal_replay_lsn() en B.

La finalidad es comprobar que B alcanzo
la posicion WAL obtenida del principal.

RESULTADO ESPERADO

PASS | Directorio de datos exclusivo
PASS | Directorio de datos exclusivo
PASS | B todavia standby
PASS | B aplico el WAL confirmado en A

INTERPRETACION

PostgreSQL B alcanzo la posicion WAL utilizada
como referencia para la comprobacion.

Esto permite verificar que los cambios anteriores,
incluida la creacion del indice, fueron reproducidos.

----------------------------------------------------------------------
PASO 10.3 - CONECTARSE A POSTGRESQL B
----------------------------------------------------------------------

En la segunda terminal PowerShell:

docker exec -it -u postgres p7-integrado-lab psql -X -h 127.0.0.1 -p 5548 -U postgres -d nobleprog_integrado -P pager=off

EXPLICACION

Este comando es equivalente a la conexion anterior.

La diferencia importante es:

-p 5548

Ese puerto corresponde a PostgreSQL B.

La primera terminal permanece conectada a A.

La segunda terminal queda conectada a B.

----------------------------------------------------------------------
PASO 10.4 - COMPROBAR QUE B ES STANDBY
----------------------------------------------------------------------

SERVIDOR B - PSQL

SELECT current_database() AS base_datos,
       inet_server_port() AS puerto,
       pg_is_in_recovery() AS en_recuperacion;

RESULTADO ESPERADO

base_datos         puerto    en_recuperacion
------------------------------------------------
nobleprog_integrado 5548     t

INTERPRETACION

Estamos conectados a PostgreSQL B.

El valor true indica que se encuentra
funcionando en modo de recuperacion.

Por tanto, continua siendo STANDBY.

----------------------------------------------------------------------
PASO 10.5 - VERIFICAR QUE EL INDICE EXISTE EN B
----------------------------------------------------------------------

SERVIDOR B - PSQL

SELECT to_regclass('negocio.pedidos_estado_fecha_idx') AS indice_replicado;

EXPLICACION

to_regclass:
Busca un objeto de tipo relacion utilizando su nombre.

Si existe, devuelve su identificacion.

Si no existe, devuelve NULL.

En este caso buscamos el indice creado en A.

RESULTADO ESPERADO

indice_replicado
--------------------------------
pedidos_estado_fecha_idx

INTERPRETACION

El indice existe en PostgreSQL B.

No fue necesario ejecutar CREATE INDEX en B.

La replicacion fisica reprodujo el cambio
realizado originalmente en el principal.

----------------------------------------------------------------------
PASO 10.6 - CONSULTAR LOS DATOS REPLICADOS
----------------------------------------------------------------------

SERVIDOR B - PSQL

SELECT c.nombre, p.id, p.fecha, p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id = p.cliente_id
WHERE p.estado = 'PAGADO'
  AND p.fecha = DATE '2026-01-15'
ORDER BY p.fecha, p.id;

RESULTADO ESPERADO

nombre    id    fecha         total
------------------------------------
Luis      102   2026-01-15    500
Ana       103   2026-01-15    150
Maria     104   2026-01-15    250

INTERPRETACION

Los datos consultados en B coinciden
con los datos confirmados en A.

No existen diferencias en los tres pedidos pagados.

----------------------------------------------------------------------
PASO 10.7 - COMPROBAR EL TOTAL EN B
----------------------------------------------------------------------

SERVIDOR B - PSQL

SELECT count(*) AS pedidos_pagados,
       sum(total) AS venta_pagada
FROM negocio.pedidos
WHERE estado = 'PAGADO'
  AND fecha = DATE '2026-01-15';

RESULTADO ESPERADO

pedidos_pagados    venta_pagada
--------------------------------
3                  900

INTERPRETACION

La replica conserva los datos necesarios
para generar el mismo reporte del principal.

----------------------------------------------------------------------
PASO 10.8 - OBSERVAR EL PLAN DE EJECUCION EN B
----------------------------------------------------------------------

SERVIDOR B - PSQL

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.nombre, p.id, p.fecha, p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id = p.cliente_id
WHERE p.estado = 'PAGADO'
  AND p.fecha = DATE '2026-01-15'
ORDER BY p.fecha, p.id;

QUE COMPROBAR

1. La consulta devuelve tres filas.

2. El indice pedidos_estado_fecha_idx esta disponible.

3. El optimizador puede utilizar el indice
   para acceder a los registros filtrados.

4. Los valores de tiempo y buffers pueden
   diferir respecto a PostgreSQL A.

INTERPRETACION

La replica fisica recibe el indice.

Sin embargo, PostgreSQL B conserva su propio
estado de memoria y condiciones de ejecucion.

Por eso los tiempos y planes medidos en A y B
no tienen que ser exactamente iguales.

----------------------------------------------------------------------
PASO 10.9 - COMPROBAR QUE B ES DE SOLO LECTURA
----------------------------------------------------------------------

SERVIDOR B - PSQL

SHOW transaction_read_only;

RESULTADO ESPERADO

transaction_read_only
---------------------
on

EXPLICACION

transaction_read_only indica si la transaccion
actual permite modificar informacion.

En una conexion normal al standby,
el valor esperado es on.

Esto significa que las operaciones de escritura
no estan permitidas.

PRUEBA DE ESCRITURA

Ejecutar exclusivamente en PostgreSQL B:

UPDATE negocio.pedidos
SET estado = 'PAGADO'
WHERE id = 101;

RESULTADO ESPERADO

ERROR: cannot execute UPDATE in a read-only transaction

INTERPRETACION

PostgreSQL B rechaza la modificacion.

El pedido 101 permanece PENDIENTE.

Este resultado demuestra que B puede ejecutar
consultas, pero no acepta escrituras mientras
continua funcionando como standby.

No se debe modificar la configuracion de B
para intentar permitir el UPDATE.

La escritura sera parte de los siguientes escenarios,
utilizando el servidor que tenga el rol PRIMARY.

13. QUE APRENDIMOS Y QUE SIGUE
======================================================================

En este ejercicio comprobamos que:

1. Una consulta puede devolver pocas filas,
   aunque la tabla contenga miles de registros.

2. EXPLAIN permite conocer el plan estimado.

3. EXPLAIN ANALYZE permite observar la ejecucion real.

4. BUFFERS permite investigar los accesos a bloques.

5. Un indice compuesto puede mejorar el filtrado.

6. El indice no modifica la informacion del negocio.

7. pg_stat_statements permite observar estadisticas acumuladas.

8. La replicacion fisica reproduce el indice en B.

9. El standby puede atender consultas de solo lectura.

10. Los resultados de A y B coinciden despues de la sincronizacion.

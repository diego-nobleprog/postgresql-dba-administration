Modulos 6 y 7: Performance Tuning y Replicacion
PostgreSQL DBA Administration

REGLA PARA COPIAR COMANDOS

Ejecutar SQL dentro de psql y comandos Docker en PowerShell.
No copiar los prompts ni las explicaciones.

Los metacomandos de psql se ejecutan INDIVIDUALMENTE.
Esto incluye \q, \set y la sentencia que termina con \gset.
Pegar esa instruccion sola, pulsar Enter y esperar el prompt
antes de pegar la siguiente consulta.

Los bloques que contienen solamente SQL pueden pegarse completos.
Un prompt con * indica una transaccion abierta.
Un prompt con - indica una sentencia incompleta.
Si hay texto accidental pendiente, pulsar Ctrl+C y esperar
el prompt antes de pegar nuevamente el SQL.


OBJETIVO

Interpretar un plan sencillo, optimizarlo con un indice
compuesto y comprobar que la replica fisica recibe el indice.

SITUACION

Necesitamos consultar tres pedidos pagados de un dia.
Existen otros 50001 pedidos que no cumplen el filtro.
Queremos reducir el trabajo sin cambiar el resultado.

PREGUNTAS

- Cuantas filas recorre PostgreSQL y cuantas devuelve?
- Un indice cambia los datos del reporte?
- Por que aparece el indice en el standby?
- Podemos escribir en ese standby?

CONCEPTOS NECESARIOS

EXPLAIN: muestra el plan estimado sin ejecutar la consulta.
EXPLAIN ANALYZE: ejecuta y muestra mediciones reales.
BUFFERS: informa accesos a buffers; hit y read son distintos.
Un read de PostgreSQL puede resolverse con cache del sistema
operativo: no demuestra por si solo una lectura fisica de disco.

Indice compuesto: indice sobre varias columnas.
Usaremos un B-tree sobre estado y fecha.

JOIN: relaciona pedidos con clientes.
SORT: ordena las filas del resultado.
AGGREGATE: calcula conteos o sumas.

Replica fisica: reproduce cambios del cluster mediante WAL.
Hot Standby: permite consultar mientras se aplica la recuperacion.

REQUISITO

Laboratorio manual creado mediante 07.00.
No haber ejecutado este escenario sobre esa carga.

============================================================
1. BEFORE - CONSULTAR LOS DATOS
============================================================

Abrir una conexion al SERVIDOR A como indica 07.00.
Todos los comandos de esta seccion son SQL o metacomandos psql.

SELECT id,cliente_id,estado,total
FROM negocio.pedidos
WHERE fecha=DATE '2026-01-15'
ORDER BY id;

RESULTADO ESPERADO

101 | 1 | PENDIENTE | 200
102 | 2 | PAGADO    | 500
103 | 1 | PAGADO    | 150
104 | 3 | PAGADO    | 250

Consultar el resumen:

SELECT c.nombre,
       count(*) AS pedidos_pagados,
       sum(p.total) AS total
FROM negocio.clientes c
JOIN negocio.pedidos p ON p.cliente_id=c.id
WHERE p.estado='PAGADO' AND p.fecha=DATE '2026-01-15'
GROUP BY c.id,c.nombre
ORDER BY c.nombre;

RESULTADO ESPERADO

Ana:   1 pedido pagado, 150.
Luis:  1 pedido pagado, 500.
Maria: 1 pedido pagado, 250.
Total: 900.

La consulta utiliza JOIN, COUNT, SUM y GROUP BY.
Solo lee datos; no modifica la informacion.

============================================================
2. DIAGNOSTICAR EL REPORTE DETALLADO
============================================================

SERVIDOR A - PSQL

EXPLAIN
SELECT c.nombre,p.id,p.fecha,p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id=p.cliente_id
WHERE p.estado='PAGADO' AND p.fecha=DATE '2026-01-15'
ORDER BY p.fecha,p.id;

Ahora ejecutar y medir:

EXPLAIN (ANALYZE,BUFFERS)
SELECT c.nombre,p.id,p.fecha,p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id=p.cliente_id
WHERE p.estado='PAGADO' AND p.fecha=DATE '2026-01-15'
ORDER BY p.fecha,p.id;

QUE OBSERVAR

- Seq Scan sobre pedidos.
- Tres filas finales.
- Filas descartadas por el filtro.
- JOIN y Sort.
- Execution Time y buffers del nodo superior.

INTERPRETACION

En la prueba temporal se descartaron 50001 filas.
El motor examino muchos pedidos para devolver solo tres.

Las estimaciones no tienen que coincidir exactamente con
las filas reales. La muestra de ANALYZE puede no representar
con precision una fecha con tan pocos registros.

El costo estimado no esta expresado en milisegundos.
No sumar buffers de padres e hijos: pueden solaparse.

Anotar tiempo, filas finales y buffers.
No exigir un tiempo minimo para declarar que hay trabajo evitable.

============================================================
3. CAMBIO - CREAR EL INDICE
============================================================

SERVIDOR A - PSQL

CREATE INDEX pedidos_estado_fecha_idx
ON negocio.pedidos(estado,fecha);

POR QUE

La consulta filtra por igualdad sobre estado y fecha.
El indice ofrece una ruta para localizar esos pedidos.

No cambia el estado de los pedidos ni el importe de venta.
Tiene costo de almacenamiento y mantenimiento en escrituras.

============================================================
4. AFTER - REPETIR LA MISMA MEDICION
============================================================

SERVIDOR A - PSQL

EXPLAIN (ANALYZE,BUFFERS)
SELECT c.nombre,p.id,p.fecha,p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id=p.cliente_id
WHERE p.estado='PAGADO' AND p.fecha=DATE '2026-01-15'
ORDER BY p.fecha,p.id;

RESULTADO ESPERADO

Un acceso que utilice pedidos_estado_fecha_idx.
Puede ser Index Scan o Bitmap Index Scan con otros nodos.
Tres filas finales, con los mismos pedidos e importes.

El JOIN puede cambiar de estrategia: es una decision del motor.
Seq Scan sobre clientes es razonable: solo tiene tres filas.

En la prueba temporal se observaron:
Antes: 7.910 ms, 323 shared hit en el nodo superior.
Despues: 0.850 ms, 5 shared hit y 2 shared read.

Son observaciones historicas, no valores de aprobacion.
La cache, el equipo y la instrumentacion afectan los tiempos.

Comprobar el total:

SELECT sum(total) AS venta_pagada
FROM negocio.pedidos
WHERE estado='PAGADO' AND fecha=DATE '2026-01-15';

RESULTADO ESPERADO: 900.

RETO PARA LOS PARTICIPANTES

Explicar por que mejoro el acceso aunque siga existiendo Sort.
El indice elegido no garantiza el orden por id.

SELECT calls,rows,
       round(total_exec_time::numeric,3) AS total_ms,
       shared_blks_hit,shared_blks_read,query
FROM pg_stat_statements
WHERE query LIKE 'SELECT c.nombre,p.id%'
ORDER BY calls DESC;

RESULTADO ESPERADO

La consulta aparece con al menos tres llamadas.
Tres ejecuciones de tres filas acumulan nueve filas.

INTERPRETACION

Estas estadisticas pertenecen a esta instancia.
No confundir el tiempo acumulado con el de una sola ejecucion.
Los literales pueden aparecer normalizados como parametros.
La extension fue precargada durante la preparacion.

6. COMPROBAR LA REPLICA
============================================================

Desde OTRA TERMINAL POWERSHELL:

& {
    $ErrorActionPreference = "Stop"
    docker exec -u postgres p7-integrado-lab bash /tmp/p7-integrado-scripts/00-sync-replica.sh
    if ($LASTEXITCODE -ne 0) { throw "No se confirmo la sincronizacion." }
}

El script espera una posicion WAL observable con limite de tiempo.
No se basa exclusivamente en dormir un numero fijo de segundos.

Abrir conexion al SERVIDOR B como indica 07.00.

SERVIDOR B - PSQL

SELECT pg_is_in_recovery();

SELECT to_regclass('negocio.pedidos_estado_fecha_idx');

SELECT c.nombre,p.id,p.fecha,p.total
FROM negocio.pedidos p
JOIN negocio.clientes c ON c.id=p.cliente_id
WHERE p.estado='PAGADO' AND p.fecha=DATE '2026-01-15'
ORDER BY p.fecha,p.id;
SELECT c.nombre,
       count(*) AS pedidos_pagados,
       sum(p.total) AS total
FROM negocio.clientes c
JOIN negocio.pedidos p ON p.cliente_id=c.id
WHERE p.estado='PAGADO' AND p.fecha=DATE '2026-01-15'
GROUP BY c.id,c.nombre
ORDER BY c.nombre;

RESULTADO ESPERADO

Recuperacion t.
Indice negocio.pedidos_estado_fecha_idx presente.
Los mismos tres pedidos y total 900.

El indice se creo en A.
B lo recibio mediante replicacion fisica.

PRUEBA NEGATIVA - SERVIDOR B, FUERA DE BEGIN

\set VERBOSITY verbose

UPDATE negocio.pedidos SET estado='PAGADO' WHERE id=101;

RESULTADO ESPERADO

ERROR 25006: no se puede ejecutar UPDATE en solo lectura.

Este error es intencional.
No significa que la replicacion haya fallado.
No intentar corregirlo cambiando la configuracion de B.

\set VERBOSITY default

COMPARACION CON ORACLE

Ambos motores usan optimizadores y planes de ejecucion.
Los nombres de operadores, costos y herramientas no son
equivalencias exactas entre productos.

Una replica fisica de Data Guard aporta una referencia
conceptual para entender la aplicacion de cambios.
No supone que configuracion ni licencias sean equivalentes.
En Oracle, consultar un physical standby mientras aplica redo
corresponde a la funcionalidad de Active Data Guard.

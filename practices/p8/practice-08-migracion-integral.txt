PostgreSQL DBA - Administracion, Performance, Backup,
Replicacion y Alta Disponibilidad

==============================================================
OBJETIVO DEL LABORATORIO
==============================================================

Vamos a migrar un sistema comercial desde un servidor PostgreSQL
de DESARROLLO hacia otro servidor PostgreSQL de PRODUCCION.

NO migraremos solamente los registros de las tablas.

Debemos conservar los objetos que hacen posible utilizar esos
registros, protegerlos y mantener su integridad.

ALCANCE EXACTO DE LA MIGRACION

1. BASES DE DATOS

   ventas_db
   reportes_db

   Son las bases que requiere el sistema comercial.

   sandbox_db NO se migrara porque es una base de pruebas.

2. SCHEMAS

   ventas_db:
     comercial
     auditoria
     reportes

   reportes_db:
     externo

   Los schemas organizan los objetos. Debemos conservarlos
   para que las referencias a tablas y funciones sigan funcionando.

3. TABLAS Y REGISTROS

   comercial.clientes
   comercial.productos
   comercial.pedidos
   comercial.detalles
   comercial.pagos
   auditoria.cambios_pedidos

   Se migraran sus definiciones y sus registros.

4. ROLES

   p8_owner
   p8_app
   p8_reader
   p8_reporter

   Los roles conservan la propiedad de objetos y los permisos
   de las aplicaciones y usuarios.

5. TABLESPACE

   p8_ts_indices

   Debe restaurarse porque forma parte de la configuracion de
   almacenamiento del origen.

   En produccion utilizara una ruta fisica diferente.

6. SECUENCIAS

   comercial.pagos_seq
   comercial.pedidos_pedido_id_seq
   auditoria.cambios_pedidos_auditoria_id_seq

   Deben conservarse sus definiciones y valores actuales.

   Una migracion que copia filas pero pierde el estado de las
   secuencias puede generar identificadores repetidos.

7. FUNCIONES, PROCEDIMIENTOS Y TRIGGERS

   comercial.total_pedido(bigint)
   comercial.registrar_pago(bigint,numeric)
   auditoria.registrar_cambio_pedido()
   comercial.pedidos.trg_pedido_estado

   Estos objetos conservan la logica del sistema.

8. VISTAS

   reportes.v_ventas_pagadas
   reportes.mv_ventas_pagadas

   La segunda es una vista materializada; tambien debemos
   conservar su contenido almacenado.

9. INDICES Y RESTRICCIONES

   Claves primarias.
   Claves foraneas.
   Restricciones CHECK.
   idx_pedidos_estado.
   idx_productos_nombre_trgm.

   Se necesitan para conservar integridad y acceso eficiente.

10. EXTENSIONES

   pg_trgm
   pg_stat_statements
   postgres_fdw

   Agregan funcionalidades utilizadas por el sistema.

11. FOREIGN DATA WRAPPER

   p8_ventas_server
   USER MAPPING de p8_reporter
   externo.pedidos

   Permiten consultar datos de otra base PostgreSQL.

   La definicion FDW se migra, pero las filas remotas
   no se almacenan dentro del respaldo de reportes_db.

12. PERMISOS Y PROPIETARIOS

   Se conservaran los privilegios ACL asociados a los objetos.

==============================================================
ESTRATEGIA DE MIGRACION
==============================================================

Generaremos UN SOLO JUEGO de respaldos definitivos:

- p8-globales.sql
- ventas_db.dump
- reportes_db.dump

Despues inspeccionaremos esos archivos para obtener su inventario.

Finalmente trasladaremos y restauraremos LOS MISMOS archivos.

No realizaremos una segunda exportacion para cada objeto.

SECCION 1: Inventario y exportacion.
SECCION 2: Restauracion.
SECCION 3: Monitoreo y comprobacion.

==============================================================
ORGANIZACION DE TERMINALES
==============================================================

TERMINAL 1

Windows PowerShell.
La utilizaremos para acceder al contenedor p8-dev-lab.

TERMINAL 2

Otra ventana Windows PowerShell.
La utilizaremos para copiar los respaldos y acceder a p8-prod-lab.

Cuando veamos:

PS C:\...>

Cuando veamos:

Estamos dentro del contenedor Linux correspondiente.

IMPORTANTE

Los comandos docker y docker cp se ejecutan en PowerShell.

Los comandos pg_dump, pg_restore, psql, mkdir y chown del
laboratorio se ejecutan dentro de Bash cuando asi se indique.

El comando exit sirve para regresar de Bash a PowerShell.

==============================================================
CONDICION INICIAL OBLIGATORIA
==============================================================

La restauracion solamente debe ejecutarse sobre un destino limpio.

Si produccion ya contiene los roles, tablespace o bases del
laboratorio, NO volveremos a ejecutar CREATE ROLE ni pg_restore -C.

La corrida validada del laboratorio ya restauro ambas bases.

Por eso, para consultar ese estado actual utilizaremos
la SECCION 3, sin repetir las operaciones de restauracion.

Las salidas documentadas proceden de la corrida satisfactoria
del 20 de noviembre de 2026.

No representan una invitacion a volver a ejecutar operaciones
destructivas o de creacion sobre el ambiente actual.

==============================================================
SECCION 1 - INVENTARIO Y EXPORTACION
==============================================================

Existen varias herramientas de inventario PostgreSQL.

psql:
  \l+ permite listar bases.
  \dn+ permite listar schemas.
  \dt+ permite listar tablas.
  \df+ permite listar funciones.
  \des+ permite listar servidores externos.

Catalogos:
  pg_database
  pg_roles
  pg_class
  pg_proc
  pg_tablespace

Sin embargo, en esta practica elegimos pg_dumpall, pg_dump
y pg_restore --list.

La razon es sencilla: podemos inventariar los mismos
respaldos definitivos que despues restauraremos.

md5 calcula una huella del contenido serializado.

Se comprueban clientes, productos, pedidos, detalles,
pagos, auditoria y vista materializada.

El hash MD5 de contenido es un control didactico,
no una firma de seguridad criptografica.

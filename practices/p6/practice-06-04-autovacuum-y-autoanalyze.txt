PRACTICA 06.04 - AUTOVACUUM Y AUTOANALYZE
Modulo 5: Mantenimiento y Autovacuum
PostgreSQL DBA Administration


OBJETIVO

Comprender como PostgreSQL realiza mantenimiento
automatico de las tablas.

Demostrar que Autovacuum y Autoanalyze realmente
se ejecutaron, utilizando contadores y fechas.

Restaurar los parametros originales del laboratorio.


SITUACION

Tenemos una tabla inicialmente vacia.

Generaremos miles de operaciones para producir
trabajo de mantenimiento.

Queremos responder:

- Que hace Autovacuum?
- Que hace Autoanalyze?
- Como sabe PostgreSQL cuando ejecutarlos?
- Podemos controlar sus umbrales?
- Como verificamos que realmente trabajaron?


CONCEPTOS NECESARIOS

AUTOVACUUM:

Es el mecanismo automatico de PostgreSQL
para realizar tareas de mantenimiento.

Entre ellas se encuentra la limpieza de
versiones obsoletas de las tablas.

Tambien participa en la prevencion de
problemas por antiguedad de XID.


AUTOANALYZE:

Es la ejecucion automatica de ANALYZE.

Actualiza estadisticas utilizadas
por el optimizador de consultas.


AUTOVACUUM_NAPTIME:

Controla el intervalo minimo aproximado
entre activaciones del lanzador de Autovacuum.

No es una garantia de ejecucion inmediata
sobre una tabla determinada.


THRESHOLD:

Es un umbral utilizado para determinar
cuando una tabla necesita mantenimiento.

Puede combinar una cantidad fija
con un factor proporcional al tamano.


SCALE FACTOR:

Factor utilizado para calcular una cantidad
adicional de cambios en funcion de
las caracteristicas de la tabla.


PG_STAT_USER_TABLES:

Vista que contiene indicadores de actividad
y mantenimiento de tablas de usuario.

Permite consultar ejecuciones manuales
y automaticas de VACUUM y ANALYZE.

============================================================
PASO 1. CONSULTAR Y CONSERVAR EL ESTADO ORIGINAL
============================================================

QUE QUEREMOS DEMOSTRAR

Antes de modificar parametros, necesitamos
conocer y conservar su valor original.

Esto nos permitira comprobar la restauracion.


COMANDO

-- Guardar temporalmente los valores originales
-- de los parametros que modificaremos.
CREATE TEMP TABLE p6_settings_before AS
SELECT
    name,
    setting,
    unit
FROM pg_settings
WHERE name IN (
    'autovacuum_naptime',
    'log_autovacuum_min_duration'
);


EXPLICACION

CREATE TEMP TABLE:

Crea una tabla temporal asociada a nuestra
sesion actual de PostgreSQL.

La utilizamos para guardar los valores BEFORE.

No es una tabla permanente del negocio.

Se eliminara automaticamente al terminar
esta conexion.


CONSULTAR EL BEFORE

-- Mostrar los valores originales.
SELECT *
FROM p6_settings_before
ORDER BY name;


RESULTADO DE REFERENCIA

autovacuum_naptime = 60 segundos.

log_autovacuum_min_duration = 600000 milisegundos.


GUARDAR LAS OPCIONES DE LA TABLA

-- Conservar las opciones actuales de auto_work.
CREATE TEMP TABLE p6_options_before AS
SELECT reloptions
FROM pg_class
WHERE oid = 'maintenance.auto_work'::regclass;

-- Mostrar las opciones originales.
SELECT *
FROM p6_options_before;


RESULTADO ESPERADO

autovacuum_enabled=false.


COMPROBAR EL ESTADO GENERAL

-- Confirmar que los mecanismos globales
-- necesarios estan habilitados.
SELECT
    current_setting('autovacuum') AS autovacuum,
    current_setting('track_counts') AS track_counts;

-- Confirmar que auto_work esta vacia.
SELECT COUNT(*) AS filas
FROM maintenance.auto_work;


RESULTADO ESPERADO

autovacuum = on.

track_counts = on.

filas = 0.


INTERPRETACION

Autovacuum esta habilitado globalmente.

Sin embargo, el mantenimiento ordinario
de auto_work fue deshabilitado durante
la preparacion del laboratorio.

Ahora podemos controlar cuando empezara
a procesarse esta tabla.


============================================================
PASO 2. ACELERAR EL CICLO DE OBSERVACION
============================================================

QUE QUEREMOS DEMOSTRAR

Queremos reducir el tiempo de espera
para observar las tareas automaticas.


COMANDOS

-- Reducir temporalmente el intervalo
-- del lanzador de Autovacuum a un segundo.
ALTER SYSTEM SET autovacuum_naptime = '1s';

-- Registrar las operaciones automaticas
-- independientemente de su duracion.
ALTER SYSTEM SET log_autovacuum_min_duration = '0';

-- Solicitar una recarga de configuracion.
SELECT pg_reload_conf();


EXPLICACION

ALTER SYSTEM:

Modifica la configuracion persistente
administrada por PostgreSQL.

pg_reload_conf():

Solicita que PostgreSQL recargue
los parametros que admiten recarga.

Un resultado true significa que se solicito
la recarga; debemos comprobar posteriormente
que los valores efectivos cambiaron.


COMPROBAR EL AFTER

-- Dar un breve margen a la recarga.
SELECT pg_sleep(1);

-- Consultar los valores efectivos.
SELECT
    name,
    setting,
    unit
FROM pg_settings
WHERE name IN (
    'autovacuum_naptime',
    'log_autovacuum_min_duration'
)
ORDER BY name;


RESULTADO ESPERADO

autovacuum_naptime = 1 segundo.

log_autovacuum_min_duration = 0.


IMPORTANTE

Estos ajustes son temporales para la capacitacion.

No representan una configuracion recomendada
para cualquier ambiente productivo.


============================================================
PASO 3. CONFIGURAR UMBRALES DE MANTENIMIENTO
============================================================

QUE QUEREMOS DEMOSTRAR

Queremos facilitar que PostgreSQL identifique
la necesidad de mantenimiento con pocos cambios.


COMANDO

-- Configurar umbrales sobre nuestra tabla.
ALTER TABLE maintenance.auto_work SET (
    autovacuum_enabled=false,
    autovacuum_vacuum_threshold=25,
    autovacuum_vacuum_scale_factor=0,
    autovacuum_vacuum_insert_threshold=-1,
    autovacuum_analyze_threshold=25,
    autovacuum_analyze_scale_factor=0
);


EXPLICACION DE CADA PARAMETRO

autovacuum_enabled=false:

Mantiene deshabilitado temporalmente
el mantenimiento automatico ordinario.

Lo habilitaremos despues de generar cambios.


autovacuum_vacuum_threshold=25:

Define una cantidad base de modificaciones
relevantes para VACUUM.


autovacuum_vacuum_scale_factor=0:

Elimina la parte proporcional del umbral
para este experimento.


autovacuum_vacuum_insert_threshold=-1:

Deshabilita el disparador de VACUUM basado
solamente en inserciones para esta tabla.


autovacuum_analyze_threshold=25:

Define una cantidad base de cambios
para solicitar Autoanalyze.


autovacuum_analyze_scale_factor=0:

Elimina la parte proporcional del calculo
del umbral de Autoanalyze.


QUE SIGNIFICA EN ESTE LABORATORIO

Cuando los cambios relevantes superen
aproximadamente 25, tendremos condiciones
para solicitar mantenimiento.

El lanzamiento real no tiene que suceder
en el mismo instante.


COMPROBAR LOS CAMBIOS

-- Consultar opciones particulares de la tabla.
SELECT reloptions
FROM pg_class
WHERE oid = 'maintenance.auto_work'::regclass;


IMPORTANTE

Estas opciones son propias de auto_work.

No debemos buscarlas como si fueran
los parametros globales de pg_settings.


============================================================
PASO 4. GENERAR CAMBIOS CON AUTOVACUUM DESHABILITADO
============================================================

QUE QUEREMOS DEMOSTRAR

Queremos generar suficientes modificaciones
antes de permitir mantenimiento automatico.


PRIMERA OPERACION

-- Insertar 12000 registros.
INSERT INTO maintenance.auto_work
SELECT
    g,
    0,
    repeat(md5(g::text),8)
FROM generate_series(1,12000) AS g;


RESULTADO ESPERADO

INSERT 0 12000


SEGUNDA OPERACION

-- Actualizar la mitad de los registros.
UPDATE maintenance.auto_work
SET version = version + 1
WHERE id <= 6000;


RESULTADO ESPERADO

UPDATE 6000


EXPLICACION

Tenemos 12000 filas visibles.

Modificamos 6000.

El UPDATE genera nuevas versiones de esas filas.

Por lo tanto, existen versiones anteriores
que eventualmente pueden necesitar limpieza.


COMPROBAR LOS DATOS

-- Verificar las filas y los cambios logicos.
SELECT
    COUNT(*) AS filas,
    SUM(version) AS suma_versiones
FROM maintenance.auto_work;


RESULTADO ESPERADO

filas = 12000.

suma_versiones = 6000.


CONSULTAR ESTADISTICAS

-- Dar tiempo a que se publiquen estadisticas.
SELECT pg_sleep(3);

-- Consultar el estado de mantenimiento.
SELECT
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    vacuum_count,
    analyze_count,
    autovacuum_count,
    autoanalyze_count
FROM pg_stat_user_tables
WHERE relid = 'maintenance.auto_work'::regclass;


EXPLICACION

n_live_tup:

Estimacion de filas vivas.

n_dead_tup:

Estimacion de versiones obsoletas.

n_mod_since_analyze:

Estimacion de cambios desde el ultimo ANALYZE.

vacuum_count:

Ejecuciones manuales de VACUUM.

analyze_count:

Ejecuciones manuales de ANALYZE.

autovacuum_count:

Ejecuciones automaticas de VACUUM.

autoanalyze_count:

Ejecuciones automaticas de ANALYZE.


RESULTADO ESPERADO

Los contadores automaticos siguen en cero.

n_dead_tup debe reflejar suficientes
versiones obsoletas para superar el umbral.

Los valores pueden tardar en actualizarse.

Si aparecen estadisticas atrasadas,
repetir la consulta antes de concluir.


============================================================
PASO 5. HABILITAR Y OBSERVAR EL MANTENIMIENTO
============================================================

QUE QUEREMOS DEMOSTRAR

Queremos comprobar que PostgreSQL realmente
ejecuta VACUUM y ANALYZE automaticamente.


COMANDO

-- Permitir mantenimiento automatico
-- ordinario sobre auto_work.
ALTER TABLE maintenance.auto_work
SET (autovacuum_enabled=true);


AHORA OBSERVAREMOS LOS CONTADORES

-- Consultar las ejecuciones automaticas.
SELECT
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    vacuum_count,
    analyze_count,
    autovacuum_count,
    autoanalyze_count,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE relid = 'maintenance.auto_work'::regclass;


RESULTADO INICIAL

Es posible que los contadores todavia
se encuentren en cero.

Eso no significa necesariamente que exista un error.

El mantenimiento automatico no tiene
una hora exacta garantizada de ejecucion.


SEGUIMIENTO

Ejecutar nuevamente la consulta anterior y,
justo despues, ejecutar:

\watch 1


QUE HACE WATCH

Repite la ultima consulta cada segundo.

Permite observar como evolucionan
los contadores de mantenimiento.

Esperar hasta observar:

autovacuum_count mayor que cero.

autoanalyze_count mayor que cero.

last_autovacuum con una fecha.

last_autoanalyze con una fecha.

Detener el seguimiento con Ctrl+C.

Usar como referencia un maximo de 90 segundos.


RESULTADO ORIGINAL DE REFERENCIA

autovacuum_count = 1.

autoanalyze_count = 1.

vacuum_count = 0.

analyze_count = 0.

n_dead_tup = 0.

n_mod_since_analyze = 0.


QUE SIGNIFICA

PostgreSQL ejecuto operaciones de mantenimiento
automatico sobre la tabla.

No tuvimos que ejecutar VACUUM manual.

Tampoco ejecutamos ANALYZE manual.

Los contadores y fechas respaldan
que realmente ocurrieron esas operaciones.


IMPORTANTE

No exigir exactamente un contador igual a uno.

Podrian ocurrir otras ejecuciones.

La condicion importante es observar
al menos una ejecucion de cada mecanismo.

Si no sucede dentro del periodo indicado,
se debe investigar.

No ejecutar mantenimiento manual para
aparentar un resultado automatico.


COMPROBAR LOS DATOS

-- Verificar que el contenido logico permanece.
SELECT
    COUNT(*) AS filas,
    SUM(version) AS suma_versiones
FROM maintenance.auto_work;


RESULTADO ESPERADO

filas = 12000.

suma_versiones = 6000.


CONCLUSION PARCIAL

Autovacuum y Autoanalyze realizaron
mantenimiento sin modificar el contenido
logico de los registros del ejercicio.


============================================================
PASO 6. RESTAURAR LA CONFIGURACION ORIGINAL
============================================================

QUE QUEREMOS DEMOSTRAR

Queremos devolver los parametros y las opciones
de la tabla a su estado anterior.

No debemos dejar ajustes de laboratorio
sin restaurar.


PRIMERA PARTE - PSQL

-- Eliminar los umbrales especiales que configuramos.
ALTER TABLE maintenance.auto_work RESET (
    autovacuum_vacuum_threshold,
    autovacuum_vacuum_scale_factor,
    autovacuum_vacuum_insert_threshold,
    autovacuum_analyze_threshold,
    autovacuum_analyze_scale_factor
);

-- Restaurar la opcion original de la tabla.
ALTER TABLE maintenance.auto_work
SET (autovacuum_enabled=false);


COMPROBAR LA RESTAURACION

-- Comparar las opciones actuales con el BEFORE.
SELECT
    c.reloptions AS opciones_actuales,
    b.reloptions AS opciones_originales,
    c.reloptions IS NOT DISTINCT FROM b.reloptions
        AS restaurado
FROM pg_class c
CROSS JOIN p6_options_before b
WHERE c.oid = 'maintenance.auto_work'::regclass;


RESULTADO ESPERADO

restaurado = true.


EXPLICACION

RESET elimina las opciones especificas
agregadas para nuestro experimento.

SET devuelve autovacuum_enabled
al valor inicial de esta tabla.

La comparacion demuestra que recuperamos
las mismas opciones registradas al comenzar.

TERCERA PARTE - REGRESAR A PSQL

-- Solicitar que PostgreSQL recargue
-- los parametros originales.
SELECT pg_reload_conf();

-- Dar tiempo a que se aplique la recarga.
SELECT pg_sleep(1);

-- Comparar parametros actuales y originales.
SELECT
    p.name,
    b.setting AS valor_original,
    p.setting AS valor_actual,
    p.setting = b.setting AS restaurado
FROM pg_settings p
JOIN p6_settings_before b
    ON p.name = b.name
ORDER BY p.name;


RESULTADO ESPERADO

Los dos parametros muestran:

restaurado = true.


QUE DEMOSTRAMOS

ANTES:

Conservamos los valores originales.

CAMBIO:

Aceleramos el mantenimiento automatico.

AFTER:

Comprobamos que los procesos trabajaron.

RESTAURACION:

Devolvimos parametros y opciones originales.

VERIFICACION:

Comprobamos que coinciden con BEFORE.


IMPORTANTE

Restaurar la configuracion no borra
los datos ni revierte el mantenimiento realizado.

La tabla conserva sus 12000 registros.

La limpieza final del laboratorio
se realiza mediante la guia 06.00.


CONCLUSION FINAL

Autovacuum y Autoanalyze permiten que
PostgreSQL realice mantenimiento automaticamente.

Los umbrales determinan cuando una tabla
se convierte en candidata.

La ejecucion real depende de la disponibilidad
de procesos y otras condiciones.

Para demostrar que una tarea realmente ocurrio,
debemos revisar contadores y fechas.

No basta con comprobar que autovacuum esta en on.


COMPARACION CON ORACLE

Oracle dispone de mecanismos automaticos
de recopilacion de estadisticas.

Autoanalyze ofrece una referencia funcional
para esa comparacion.

Autovacuum tambien participa en limpieza
de versiones y prevencion de problemas XID.

Por tanto, no equivale solamente a
la recopilacion automatica de estadisticas
que realiza Oracle.

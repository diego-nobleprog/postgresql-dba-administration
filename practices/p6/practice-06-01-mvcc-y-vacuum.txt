PRACTICA 06.01 - MVCC Y VACUUM

SITUACION Y PREGUNTA CENTRAL

Una tabla recibe cambios mientras otra sesion conserva una lectura anterior.
¿Por que VACUUM no puede retirar inmediatamente todas las versiones antiguas?

OBJETIVO

Distinguir filas visibles, versiones obsoletas y espacio reutilizable.
Observar el efecto de una transaccion prolongada sobre la limpieza.

PREPARACION

Usar el laboratorio de 06.00 con su carga inicial.
Esta guia corresponde al recorrido interactivo.
No ejecutar tambien 01-mvcc-vacuum.sh sobre la misma carga.

Abrir dos terminales PowerShell y conectar A y B con:

docker exec -it -u postgres p6-maintenance-lab psql -X -h /tmp/nobleprog-p6-lab/socket -p 5546 -U postgres -d nobleprog_maintenance_scenarios

En ambas sesiones:

\pset pager off

1. ESTABLECER UN SNAPSHOT - PSQL A

SET application_name='p6_manual_A';
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*),sum(version) FROM maintenance.mvcc_work;

Resultado esperado: 10000 filas y suma de versiones 0.
Mantener abierta esta transaccion. El primer SELECT establece el snapshot.
REPEATABLE READ permite comparar las dos consultas de A con la misma vista.

2. CAMBIAR Y CONFIRMAR DATOS - PSQL B

SET application_name='p6_manual_B';

UPDATE maintenance.mvcc_work
SET version=version+1 WHERE id<=2000;

DELETE FROM maintenance.mvcc_work
WHERE id BETWEEN 2001 AND 4000;

SELECT count(*),sum(version) FROM maintenance.mvcc_work;

B trabaja con autocommit fuera de BEGIN.
Resultado: UPDATE 2000, DELETE 2000, 8000 filas visibles y suma 2000.
Las actualizaciones generan versiones nuevas; las anteriores y las filas
eliminadas todavia pueden ser necesarias para A.

3. IDENTIFICAR EL HORIZONTE RETENIDO - PSQL B

SELECT pid,application_name,state,backend_xmin,
       age(backend_xmin) AS xmin_age,
       clock_timestamp()-xact_start AS transaction_age
FROM pg_stat_activity
WHERE application_name='p6_manual_A';

A debe aparecer idle in transaction y con backend_xmin no nulo.
Esto identifica una transaccion que conserva un horizonte de visibilidad.
Su duracion es una senal de diagnostico; no se debe terminar una sesion
de negocio sin analizar su funcion y el efecto de la cancelacion.

VACUUM (VERBOSE, INDEX_CLEANUP ON) maintenance.mvcc_work;

SELECT n_live_tup,n_dead_tup,vacuum_count
FROM pg_stat_user_tables
WHERE relid='maintenance.mvcc_work'::regclass;

Evidencia temporal: 4000 versiones dead but not yet removable.
VACUUM se ejecuto, pero no pudo retirar versiones necesarias para A.
Su ejecucion exitosa no significa que todas las versiones fueran removibles.

4. VERIFICAR LA VISTA ANTERIOR Y LIBERARLA - PSQL A

SELECT count(*),sum(version) FROM maintenance.mvcc_work;
COMMIT;

A debe seguir viendo 10000 y 0 antes del COMMIT.
B ya veia 8000 y 2000: las consultas tienen snapshots distintos.
El COMMIT termina la necesidad de conservar la vista de A.

5. LIMPIAR LAS VERSIONES YA REMOVIBLES - PSQL B

VACUUM (VERBOSE, INDEX_CLEANUP ON) maintenance.mvcc_work;

SELECT count(*),sum(version) FROM maintenance.mvcc_work;
SELECT n_live_tup,n_dead_tup,vacuum_count
FROM pg_stat_user_tables
WHERE relid='maintenance.mvcc_work'::regclass;

Resultado esperado: 8000 filas reales y ninguna version obsoleta pendiente
en este experimento sin otras transacciones reteniendo snapshots.
La evidencia temporal confirmo la eliminacion de 4000 versiones.

COUNT(*) mide las filas visibles para esa consulta.
n_live_tup y n_dead_tup son estimaciones y pueden diferir del conteo.
Los informes de VACUUM tambien pueden incorporar estimaciones al omitir
paginas; no interpretar una diferencia aislada como perdida de filas.

6. COMPROBAR LA REUTILIZACION - PSQL B

SELECT pg_relation_size('maintenance.mvcc_work') AS heap_before \gset

INSERT INTO maintenance.mvcc_work
SELECT g,0,repeat(md5(g::text),8)
FROM generate_series(10001,12000) AS g;

SELECT count(*) FROM maintenance.mvcc_work;

SELECT :'heap_before'::bigint AS before_bytes,
       pg_relation_size('maintenance.mvcc_work') AS after_bytes,
       pg_relation_size('maintenance.mvcc_work')
           <= :'heap_before'::bigint AS reused_without_growth;

Resultado esperado: 10000 filas y reused_without_growth=true.
En la prueba temporal el heap permanecio en 3645440 bytes.
El valor exacto es una referencia de esa ejecucion, no una constante universal.

La limpieza habilito espacio interno para nuevas filas.
Reutilizar espacio no exige reducir el archivo de la tabla.

7. PRUEBA NEGATIVA CONTROLADA - PSQL B

BEGIN;
VACUUM maintenance.mvcc_work;

Se espera: VACUUM cannot run inside a transaction block.
Consultar el detalle del ultimo error y cerrar la transaccion fallida:

\errverbose
ROLLBACK;

SQLSTATE esperado: 25001.
Es una restriccion demostrada, no un fallo funcional del laboratorio.
El ROLLBACK es necesario antes de continuar usando esa transaccion.

COMPARACION CON ORACLE

Ambos motores ofrecen lecturas consistentes mediante versiones.
Oracle reconstruye vistas consistentes utilizando undo.
En este escenario PostgreSQL conserva versiones en el almacenamiento de
la tabla y VACUUM retira las que ya no son necesarias.
No trasladar directamente conceptos de undo retention a parametros de VACUUM.

CONCLUSION Y CONTINUIDAD

Los participantes deben explicar por que el primer VACUUM no pudo limpiar
todo, por que el segundo si y como se reutilizo el espacio.

Cerrar A y B con \q. Continuar con 06.02 sin recrear el laboratorio.
La restauracion global y el cierre estan en 06.00.

Comprender y verificar experimentalmente los procesos, memoria, WAL, checkpoints, MVCC, estructura física, bases de datos, schemas, tablespaces y estadísticas de PostgreSQL. 1. ARQUITECTURA Y PROCESOS
====================================================================
OBJETIVO: distinguir el proceso principal, procesos auxiliares y backends de clientes.

BEFORE - INSPECCIÓN DESDE EL SISTEMA OPERATIVO

docker top postgresql-dba

Identificar procesos postgres, checkpointer, background writer, WAL writer, autovacuum y backends. La lista puede cambiar entre ejecuciones.

INSPECCIÓN SQL

@'
SELECT pid, backend_type, state, wait_event_type, wait_event
FROM pg_stat_activity
ORDER BY backend_type, pid;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

PRUEBA DE UNA SESIÓN ACTIVA
Abrir una terminal PowerShell adicional y ejecutar:

docker exec -it postgresql-dba psql -U postgres -d postgres

Dentro de psql, ejecutar:
SELECT pg_backend_pid();
SELECT pg_sleep(30);

Mientras duerme, desde otra terminal ejecutar:

@'
SELECT pid, backend_type, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE datname = 'postgres'
ORDER BY pid;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: identificar el PID de la sesión de prueba. El proceso backend atiende la conexión del cliente; no confundirlo con el proceso principal.

2. GESTIÓN DE MEMORIA
====================================================================
OBJETIVO: distinguir memoria compartida, memoria por operación y estimación de caché del SO.

@'
SELECT name, setting, unit, context, source
FROM pg_settings
WHERE name IN (
  'shared_buffers', 'work_mem', 'maintenance_work_mem',
  'effective_cache_size', 'temp_buffers'
)
ORDER BY name;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VALORES OBSERVADOS EN EL LABORATORIO: shared_buffers=128MB; work_mem=4MB; maintenance_work_mem=64MB; effective_cache_size=4GB; temp_buffers=8MB. Confirmar los valores reales de su entorno.

CONCEPTO: shared_buffers es memoria compartida del servidor; work_mem es un límite por operación de ordenamiento/hash (pueden existir varias por consulta y sesión); maintenance_work_mem afecta operaciones de mantenimiento; effective_cache_size es una estimación para el planificador, no memoria reservada.

3. WORK_MEM, MAINTENANCE_WORK_MEM Y SHARED_BUFFERS
====================================================================
OBJETIVO: comparar ordenamientos en disco y memoria, construcción de índices y caché.

PREPARACIÓN DE DATOS (ejecutar una sola vez)

@'
CREATE SCHEMA IF NOT EXISTS lab_p2;
CREATE TABLE IF NOT EXISTS lab_p2.memory_test (
  id INTEGER PRIMARY KEY,
  description TEXT NOT NULL
);
INSERT INTO lab_p2.memory_test (id, description)
SELECT g, repeat(md5(g::text), 10)
FROM generate_series(1, 100000) AS g
ON CONFLICT (id) DO NOTHING;
SELECT COUNT(*) FROM lab_p2.memory_test;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

NOTA: la generación de datos de esta guía es reproducible; si ya existe la tabla de la práctica, no sobrescribirla. La distribución exacta y los tiempos pueden diferir.

3A. WORK_MEM - BEFORE / CHANGE / AFTER / RESTORE

@'
SHOW work_mem;
SET max_parallel_workers_per_gather = 0;
SET work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_p2.memory_test ORDER BY description;
SET work_mem = '64MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_p2.memory_test ORDER BY description;
RESET work_mem;
RESET max_parallel_workers_per_gather;
SHOW work_mem;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: comparar Sort Method (external merge / Disk frente a quicksort / Memory, cuando el plan use sort) y Execution Time. En la validación del instructor se observaron aproximadamente 234 ms frente a 119 ms; no son valores garantizados. Si existe un índice que satisface ORDER BY, el plan puede evitar el sort: revisar el plan antes de sacar conclusiones.

3B. MAINTENANCE_WORK_MEM - comparar construcción de índice

Para una comparación reproducible, usar el mismo índice, reconstruido en cada escenario. Ejecutar solo en laboratorio; DROP INDEX afecta temporalmente disponibilidad del índice.

@'
SHOW maintenance_work_mem;
SET maintenance_work_mem = '1MB';
DROP INDEX IF EXISTS lab_p2.idx_memory_test_description;
\timing on
CREATE INDEX idx_memory_test_description ON lab_p2.memory_test(description);
DROP INDEX lab_p2.idx_memory_test_description;
SET maintenance_work_mem = '128MB';
CREATE INDEX idx_memory_test_description ON lab_p2.memory_test(description);
\timing off
RESET maintenance_work_mem;
SHOW maintenance_work_mem;
SELECT pg_size_pretty(pg_relation_size('lab_p2.idx_memory_test_description')) AS index_size;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: registrar ambos tiempos y el tamaño del índice. Una sola ejecución no permite inferir una mejora universal. En la ejecución original se observaron ~375 ms y ~302 ms.

3C. SHARED_BUFFERS Y CACHE HIT

@'
SELECT name, setting, unit, context FROM pg_settings WHERE name = 'shared_buffers';
SELECT current_setting('block_size') AS block_size_bytes;
SELECT datname, blks_hit, blks_read,
  round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS cache_hit_pct
FROM pg_stat_database WHERE datname = current_database();
EXPLAIN (ANALYZE, BUFFERS) SELECT sum(id) FROM lab_p2.memory_test;
EXPLAIN (ANALYZE, BUFFERS) SELECT sum(id) FROM lab_p2.memory_test;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: comparar shared hit/read en ambos planes. En la práctica original se observaron 3449 hits por escaneo. shared_buffers=128MB equivale a 16384 páginas de 8KB. Cambiar shared_buffers requiere reinicio: aquí solo se inspecciona. El hit ratio no mide por sí solo la calidad de las consultas ni la caché del sistema operativo.

4. WAL Y CHECKPOINTS
====================================================================
OBJETIVO: observar configuración WAL, crecimiento de LSN y efecto de un checkpoint manual.

PREPARACIÓN

@'
CREATE TABLE IF NOT EXISTS lab_p2.wal_test (
  id BIGSERIAL PRIMARY KEY,
  description TEXT NOT NULL
);
SELECT name, setting, unit
FROM pg_settings
WHERE name IN ('wal_level','fsync','synchronous_commit','full_page_writes',
               'wal_segment_size','max_wal_size','min_wal_size',
               'checkpoint_timeout','checkpoint_completion_target')
ORDER BY name;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

BEFORE / CHANGE / AFTER - LSN

@'
SELECT pg_current_wal_lsn() AS lsn_before \gset
SELECT :'lsn_before' AS lsn_before;
INSERT INTO lab_p2.wal_test(description)
SELECT repeat(md5(g::text), 5) FROM generate_series(1, 10000) AS g;
SELECT pg_current_wal_lsn() AS lsn_after \gset
SELECT :'lsn_after' AS lsn_after,
       pg_wal_lsn_diff(:'lsn_after', :'lsn_before') AS wal_bytes_generated;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: WAL generado > 0. El valor varía según estado del clúster y actividad concurrente.

CHECKPOINT - observar contadores antes y después

@'
SELECT num_timed, num_requested, num_done, buffers_written
FROM pg_stat_checkpointer;
CHECKPOINT;
SELECT num_timed, num_requested, num_done, buffers_written
FROM pg_stat_checkpointer;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: num_requested y num_done deberían incrementarse por el checkpoint manual. No ejecutar CHECKPOINT repetidamente en producción solo para experimentar.

5. BACKGROUND WRITER, WAL WRITER Y CHECKPOINTER
====================================================================
OBJETIVO: identificar responsabilidades y observar métricas de I/O por tipo de backend.

@'
SELECT pid, backend_type
FROM pg_stat_activity
WHERE backend_type IN ('background writer', 'walwriter', 'checkpointer')
ORDER BY backend_type;
SELECT backend_type, object, context,
       sum(writes) AS writes, sum(fsyncs) AS fsyncs
FROM pg_stat_io
WHERE backend_type IN ('client backend', 'walwriter', 'checkpointer', 'background writer')
GROUP BY backend_type, object, context
ORDER BY backend_type, object, context;
SELECT buffers_clean, maxwritten_clean FROM pg_stat_bgwriter;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

CHANGE - generar actividad y volver a observar

@'
INSERT INTO lab_p2.wal_test(description)
SELECT repeat(md5(g::text), 5) FROM generate_series(1, 10000) AS g;
SELECT backend_type, object, context,
       sum(writes) AS writes, sum(fsyncs) AS fsyncs
FROM pg_stat_io
WHERE backend_type IN ('client backend', 'walwriter', 'checkpointer', 'background writer')
GROUP BY backend_type, object, context
ORDER BY backend_type, object, context;
SELECT buffers_clean, maxwritten_clean FROM pg_stat_bgwriter;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: registrar las diferencias entre mediciones, sin exigir que todos los procesos incrementen contadores. En PostgreSQL 18 las métricas writes/fsyncs por backend están en pg_stat_io; NO buscar columnas wal_write/wal_sync en pg_stat_wal. La actividad depende de la carga y del momento de muestreo.

6. MVCC: COMMIT, ROLLBACK Y VISIBILIDAD
====================================================================
OBJETIVO: observar versiones de filas y aislamiento READ COMMITTED usando dos sesiones.

PREPARACIÓN (PowerShell)

@'
CREATE TABLE IF NOT EXISTS lab_p2.mvcc_test (
  id INTEGER PRIMARY KEY,
  account_name TEXT NOT NULL,
  balance NUMERIC(12,2) NOT NULL
);
INSERT INTO lab_p2.mvcc_test(id, account_name, balance)
VALUES (1, 'Cuenta Demo', 1000.00)
ON CONFLICT (id) DO NOTHING;
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

Si la tabla ya fue utilizada, el saldo inicial puede ser 1500.00. Para repetir exactamente el experimento desde 1000.00, restaurar primero con un UPDATE explícito y registrar el nuevo xmin/ctid; no asumir los IDs de transacción del instructor.

SESIÓN A - abrir PowerShell A:

docker exec -it postgresql-dba psql -U postgres -d postgres

Ejecutar cada sentencia por separado:
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;
BEGIN;
UPDATE lab_p2.mvcc_test SET balance = 1500.00 WHERE id = 1;
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;

Dejar A abierta con prompt postgres=*#; NO ejecutar COMMIT todavía.

SESIÓN B - abrir PowerShell B:

docker exec -it postgresql-dba psql -U postgres -d postgres

Ejecutar:
SELECT pg_backend_pid();
SHOW transaction_isolation;
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;

VERIFY: B ve el saldo confirmado anterior (1000.00 si partimos de ese valor), aunque A ve 1500.00. El xmax de la versión anterior puede reflejar la transacción aún no confirmada.

VOLVER A A:
COMMIT;

VOLVER A B:
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;

VERIFY: B ahora ve 1500.00. En READ COMMITTED, cada sentencia obtiene su propia instantánea de datos confirmados.

ROLLBACK - EN A:
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;
BEGIN;
UPDATE lab_p2.mvcc_test SET balance = 2000.00 WHERE id = 1;
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;
ROLLBACK;
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;

VERIFY - EN B:
SELECT id, balance, xmin, xmax, ctid FROM lab_p2.mvcc_test WHERE id = 1;

VERIFY: ambas sesiones ven 1500.00. xmax puede contener el ID de una transacción abortada; no interpretar xmax sin comprobar el estado de la transacción. Una versión abortada puede permanecer físicamente hasta mantenimiento posterior.
Cerrar ambas sesiones con \q.

9. CATÁLOGOS, ESTADÍSTICAS Y ANALYZE
====================================================================
OBJETIVO: diferenciar metadatos del catálogo y contadores de actividad, y actualizar estimaciones del planificador.

9A. CONSULTAS DE DIAGNÓSTICO

@'
SELECT n.nspname AS schema_name, c.relname AS table_name,
       c.oid AS relation_oid, c.reltuples AS estimated_rows,
       c.relpages AS estimated_pages
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'lab_p2' AND c.relkind = 'r'
ORDER BY c.relname;
SELECT schemaname, relname, seq_scan, idx_scan,
       n_tup_ins, n_tup_upd, n_tup_del, n_dead_tup
FROM pg_stat_user_tables
WHERE schemaname = 'lab_p2' ORDER BY relname;
SELECT schemaname, relname, indexrelname,
       idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'lab_p2' ORDER BY relname, indexrelname;
SELECT datname, numbackends, xact_commit, xact_rollback,
       blks_read, blks_hit, temp_files, deadlocks
FROM pg_stat_database WHERE datname = current_database();
SELECT pid, usename, datname, state, wait_event_type, wait_event
FROM pg_stat_activity WHERE datname = current_database() ORDER BY pid;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

INTERPRETACIÓN:
- pg_class.reltuples/relpages: estimaciones, no recuentos exactos.
- pg_stat_user_tables: contadores de operaciones y estimaciones de tuplas muertas.
- pg_stat_user_indexes: actividad de índices, no equivale directamente a cantidad de sentencias SQL.
- pg_stat_database: métricas acumuladas por base de datos.
- Cache hit ratio = 100 * blks_hit / (blks_hit + blks_read); no mide caché del SO ni garantiza buen rendimiento.

9B. BEFORE / CHANGE / AFTER / VERIFY CON ANALYZE

@'
SELECT oid::regclass AS relation, reltuples AS estimated_rows,
       relpages AS estimated_pages
FROM pg_class WHERE oid = 'lab_p2.mvcc_test'::regclass;
ANALYZE lab_p2.mvcc_test;
SELECT oid::regclass AS relation, reltuples AS estimated_rows,
       relpages AS estimated_pages
FROM pg_class WHERE oid = 'lab_p2.mvcc_test'::regclass;
SELECT schemaname, relname, last_analyze, analyze_count,
       n_live_tup, n_dead_tup
FROM pg_stat_user_tables
WHERE schemaname = 'lab_p2' AND relname = 'mvcc_test';
SELECT count(*) AS actual_rows FROM lab_p2.mvcc_test;
'@ | docker exec -i postgresql-dba psql -v ON_ERROR_STOP=1 -U postgres -d postgres

VERIFY: en la ejecución original reltuples pasó de -1 a 1 y relpages de 0 a 1; analyze_count llegó a 1; n_live_tup=1, n_dead_tup=2, count(*)=1. Si ya se ejecutó ANALYZE, el BEFORE puede ser 1/1 y analyze_count mayor. ANALYZE actualiza estadísticas, NO elimina tuplas muertas; VACUUM cumple otra función.
